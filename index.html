Abstract

This document specifies the Typed Context Protocol (tcxp): the syntax of tcxp addresses, how they are written, encoded and sent over a network, the context and spike objects they carry, and the sensor objects and governors that evaluate them. It also defines the tcxp document and its proposed media type, text/tcxp.

Status of This Document

This specification was published by the Typed Context Protocol Community Group. It is not a W3C Standard nor is it on the W3C Standards Track. Please note that under the W3C Community Contributor License Agreement (CLA) there is a limited opt-out and other conditions apply. Learn more about W3C Community and Business Groups.

This is an alpha draft. Every rule in it is a design proposal verified by the editors; implementation experience and test results will be reported in later drafts. Each rule is identified by its tcxp address, tcxp://tcxp.org/rule/N, which is permanent once published, and can be linked at #rule-N.

GitHub Issues are preferred for discussion of this specification.

1. Conformance

As well as sections marked as non-normative, all authoring guidelines, diagrams, examples, and notes in this specification are non-normative. Everything else in this specification is normative.

Every rule in this document, identified by its tcxp://tcxp.org/rule/ address, is normative. Breaking a rule breaks the protocol.

2. Foundations

2.1 tcxp://tcxp.org/rule/1

The Typed Context Protocol (tcxp) is a set of guarantees, enforced by logical rules, to observe, measure, and engineer interactions with Typed Context Objects over time.

As a protocol, tcxp allows any design choice except breaking these rules. Breaking a rule breaks the protocol.

3. Addresses

3.1 tcxp://tcxp.org/rule/0

A tcxp address is tcxp: followed by a ground and a path, then an optional ?<json>. The ground is / (virtual), // (network) or /// (local). An @ at the start of the path's second segment makes the address a call.

Every combination of space and call, shown up to the optional ?<json>:

AddressSpaceGroundCallPath
tcxp:/example.com/fn/check-forecastvirtual/noexample.com/fn/check-forecast
tcxp:/example.com/@fn/check-forecastvirtual/yesexample.com/@fn/check-forecast
tcxp:/foo/barvirtual/nofoo/bar
tcxp:/foo/@barvirtual/yesfoo/@bar
tcxp://example.com/fn/check-forecastnetwork//noexample.com/fn/check-forecast
tcxp://example.com/@fn/check-forecastnetwork//yesexample.com/@fn/check-forecast
tcxp://foo/barnetwork//nofoo/bar
tcxp://foo/@barnetwork//yesfoo/@bar
tcxp:///example.com/fn/check-forecastlocal///noexample.com/fn/check-forecast
tcxp:///example.com/@fn/check-forecastlocal///yesexample.com/@fn/check-forecast
tcxp:///foo/barlocal///nofoo/bar
tcxp:///foo/@barlocal///yesfoo/@bar

3.2 tcxp://tcxp.org/rule/2

Every tcxp address starts with tcxp:, in lowercase, with nothing before it.

The scheme name tells any software that the rest of the string is a tcxp address. tcxp is provisionally registered with IANA (2026-10-09). Software reading an address should also accept an uppercase scheme, since URI schemes are case-insensitive, but addresses are always written in lowercase.

3.3 tcxp://tcxp.org/rule/3

Two slashes after tcxp: mean a network address. tcxp://<domain>/… belongs to whoever owns <domain>. Where tcxp is not supported natively, tcxp://<path> is sent to https://<path>.

This works the same way as https://: whoever controls the domain controls every name under it, with no registration needed. The domain is written in lowercase, with no user name or port. The path is everything after the ground, and it is percent-encoded when sent. For example, tcxp://example.com/@fn/check-forecast belongs to example.com, and where tcxp is not supported natively it is sent to:

https://example.com/@fn/check-forecast

3.4 tcxp://tcxp.org/rule/5

A path is everything after the ground, up to the ? if there is one: the boundary and the pointer, written as segments separated by /. Every segment has at least one character, and segments are case-sensitive.

A path names a thing, for example tcxp://example.com/forecasts/q3/v2. Because every segment has at least one character, a path never contains //, never ends with /, and always has at least two segments: the boundary and the pointer. Forecast and forecast are different segments. The @ that marks a call is syntax, not part of a segment's name. A segment is written in plain form, and is percent-encoded only where a URI is required. For example, plain and then as a URI:

tcxp://example.com/notes/My Notes
tcxp://example.com/notes/My%20Notes

3.5 tcxp://tcxp.org/rule/15

Three slashes after tcxp: mean a local address: a file on the local machine, for example tcxp:///projects/docs/rules.tcxp. It has an empty host and is resolved on the local machine, never over a network.

This is the same form as file:/// ([RFC8089]): an empty host followed by an absolute path. Relative paths such as ../rules.tcxp are never used. A local address is written in plain form, for example tcxp:///projects/My Notes.txt. With the @, the address is a call to a file on the local machine, not to a member in memory: tcxp:///foo/@bar is a local call, and tcxp:/foo/@bar is a virtual call.

3.6 tcxp://tcxp.org/rule/18

The slashes after tcxp: follow standard URI syntax (RFC 3986, section 3): // is followed by a host, /// is an empty host followed by an absolute path, and / is an absolute path with no host.

These are the same forms file: uses ([RFC8089]): file:///etc/hosts has an empty host, and file:/etc/hosts has no host. Both name the same file. In tcxp, the three forms mean different things: a network address, a local address and a virtual address.

3.7 tcxp://tcxp.org/rule/19

Every tcxp address has the form tcxp:<ground><boundary>/<optional @><pointer>, followed by an optional ?<json>. When present, <json> is a JSON object with exactly two keys: params, an array of key-value pairs, and state, one object. An @ right after the boundary makes the address a call, and it is the only @ before the ?.

The ground is / (virtual), // (network) or /// (local). The boundary is the first segment after the ground, such as example.com or foo, and the pointer is the rest of the path. params holds the inputs, in order, and state holds the state before the call. An address without @ is a reference, or a call written down but not made. Values inside the JSON may contain @. The JSON is in canonical form ([RFC8785]). For example, decoded so it can be read:

tcxp:/foo/@bar?{"params":[{"key":"x","value":1}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}

is the call:

tcxp.foo.bar({ params: [{ key: "x", value: 1 }], state: { context: { … } } })

The same address without the @ is that call written down but not made. Because a list's order is part of the object, swapping two entries in params makes a different call.

3.8 tcxp://tcxp.org/rule/20

A tcxp address is written and read in plain form. It is percent-encoded only where a URI is required, which gives its URI form. The @ at the start of the path's second segment is syntax, like / and ?: it marks a call and is never part of a name.

The governor reads the plain form, so virtual and local addresses are never percent-encoded, and neither is any address written in a document. An address is percent-encoded only where a URI is required. Its /, @ and ? stay as they are, because they are syntax. Each pair below shows the plain form, then the same address as a URI.

Nothing changes, because there is no name character or JSON to encode:

tcxp://test.com/@hello
tcxp://test.com/@hello

The space in the name is encoded; the @ is not:

tcxp://test.com/My Notes/@hello
tcxp://test.com/My%20Notes/@hello

The JSON is encoded; the @ and the ? are not:

tcxp://test.com/@hello?{"params":[{"key":"name","value":"Ron Itelman"}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}
tcxp://test.com/@hello?%7B%22params%22%3A%5B%7B%22key%22%3A%22name%22%2C%22value%22%3A%22Ron%20Itelman%22%7D%5D%2C%22state%22%3A%7B%22context%22%3A%7B%22decide%22%3A%5B%5D%2C%22intent%22%3A%5B%5D%2C%22observe%22%3A%5B%5D%2C%22reason%22%3A%5B%5D%2C%22trace%22%3A%5B%5D%7D%7D%7D

Both are the call:

hello({
  params: [
    { key: "name", value: "Ron Itelman" }
  ],
  state: {
    context: { decide: [], intent: [], observe: [], reason: [], trace: [] }
  }
})

Because the @ is syntax, no name in the path contains @.

4. Calls

4.1 tcxp://tcxp.org/rule/8

A tcxp address has no length limit. A network address is sent to its domain with the HTTP QUERY method, so nothing is lost however long it is.

The request target is the address up to the ?, percent-encoded, at https://. The JSON after the ? is the request body, with media type application/json. QUERY ([RFC10008]) is safe and idempotent like GET, but carries a body, so a long address is never cut off. For example, this plain address:

tcxp://example.com/@fn/check-forecast?{"params":[{"key":"quarter","value":"q3"}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}

is sent as:

fetch("https://example.com/@fn/check-forecast", {
  method: "QUERY",
  headers: { "Content-Type": "application/json" },
  body: '{"params":[{"key":"quarter","value":"q3"}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}'
})

4.2 tcxp://tcxp.org/rule/21

params is an array of key-value pairs. Each entry is a JSON object with exactly two keys: key, a string, and value, any JSON value. The entries are the inputs, in order.

The same call in three forms: JavaScript, the plain address, and the address as a URI.

JavaScript:

hello({
  params: [
    { key: "phrase-you-expect", value: "world" },
    { key: "count", value: 2 }
  ],
  state: {
    context: { decide: [], intent: [], observe: [], reason: [], trace: [] }
  }
})

Plain:

tcxp://test.com/@hello?{"params":[{"key":"phrase-you-expect","value":"world"},{"key":"count","value":2}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}

URI:

tcxp://test.com/@hello?%7B%22params%22%3A%5B%7B%22key%22%3A%22phrase-you-expect%22%2C%22value%22%3A%22world%22%7D%2C%7B%22key%22%3A%22count%22%2C%22value%22%3A2%7D%5D%2C%22state%22%3A%7B%22context%22%3A%7B%22decide%22%3A%5B%5D%2C%22intent%22%3A%5B%5D%2C%22observe%22%3A%5B%5D%2C%22reason%22%3A%5B%5D%2C%22trace%22%3A%5B%5D%7D%7D%7D

"world" is a string and 2 is a number: each value keeps its JSON type.

5. Context

5.1 tcxp://tcxp.org/rule/7

The context is one JSON object with exactly five lists: intent, observe, reason, decide and trace. It is held by the context key of state, and context is the only key in state.

All five lists are always present, even when empty, so a reader never has to guess whether a missing list means "none" or "not sent." Reading the context never fetches any address in it. For example, a call with an empty context, in plain form:

tcxp://example.com/@fn/check-forecast?{"params":[{"key":"quarter","value":"q3"}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}

5.2 tcxp://tcxp.org/rule/13

Every timestamp is written in UTC as defined by [RFC3339], with milliseconds and a trailing Z, and is exactly 24 characters long, for example 2026-10-10T16:35:12.345Z.

The shape is YYYY-MM-DDTHH:MM:SS.sssZ. Milliseconds are always three digits, even when they are zero (.000), and UTC is always written as Z, never as +00:00. Because there is one format with a fixed length, each moment has exactly one spelling, and sorting timestamps as text puts them in time order.

5.3 tcxp://tcxp.org/rule/14

Every entry in the five lists of a context and in the four facets of a spike is a row: a JSON object with exactly two keys, fingerprint and ref. ref is the tcxp address of what the row is about, and fingerprint records what left the row there.

fingerprint is a JSON object. Each key is a tcxp address naming what it records, and each value is any JSON value. Every fingerprint has the key tcxp://tcxp.org/fingerprint/when, whose value is the timestamp at which the row was written, so every row can be sorted by time. Any other keys are up to whoever writes the row. A JSON object has no order and never repeats a key, so canonical form gives each fingerprint exactly one spelling; to record several values for one key, such as two authors, use an array. A row's position in its list is its index, so rows have no index key. For example, a row that also records who wrote it:

{"fingerprint":{"tcxp://example.com/fingerprint/who":"tcxp://example.com/people/ron","tcxp://tcxp.org/fingerprint/when":"2026-10-11T13:06:04.217Z"},"ref":"tcxp://example.com/units/celsius"}

6. Spikes

6.1 tcxp://tcxp.org/rule/9

A spike has exactly four facets, as the keys data, meaning, structure and ground.

A spike is the object an observation creates. Each facet is an array of objects, and each object in it is a row, so a facet can hold any number of entries. All four keys are always present, in lowercase with exactly these names, so any reader is guaranteed to find them. A spike with a missing key, an extra key, or a key spelled differently, such as Meaning or Ground, is rejected.

6.2 tcxp://tcxp.org/rule/10

data is the anchor facet: it is what gets matched against the sensor object. meaning, structure and ground are the context facets, built around the anchor.

If the sensor object has the rule "MATCH the word yesterday," the anchor is the observed word yesterday, and the context facets are built around it. Only the anchor is matched against the sensor object; the context facets describe the anchor, and are never matched in its place.

6.3 tcxp://tcxp.org/rule/22

Each row in meaning refers to a semantic or pragmatic reference for the anchor, readable by a person either where it points or in the address itself.

Any tcxp address may be used, and how the addresses are named and organized is up to whoever writes them. For example, a sensor observes a temperature column, but the numbers alone do not say whether they are Celsius or Fahrenheit. A row in the spike's meaning facet says so:

{"data":[{"fingerprint":{"tcxp://tcxp.org/fingerprint/when":"2026-10-11T13:06:04.217Z"},"ref":"tcxp://example.com/sensors/thermo-1/temperature"}],"ground":[],"meaning":[{"fingerprint":{"tcxp://tcxp.org/fingerprint/when":"2026-10-11T13:06:04.217Z"},"ref":"tcxp://example.com/units/celsius"}],"structure":[]}

Without that row, a reader would have to guess the unit.

6.4 tcxp://tcxp.org/rule/23

Each row in structure refers to a schema the anchor conforms to, such as a regular expression or a JSON Schema.

A schema says what shape the anchor has, so a reader can check it before relying on it. Each rule of the shape can be its own row. For example, a row that points to a JSON Schema the anchor validates against:

{"fingerprint":{"tcxp://tcxp.org/fingerprint/when":"2026-10-11T13:06:04.217Z"},"ref":"tcxp://example.com/schemas/temperature"}

6.5 tcxp://tcxp.org/rule/24

Each row in ground refers to a real-world condition that grounds the data, meaning and structure to a decision: something a reader must account for before acting on the anchor.

The data, its meaning and its structure can all be correct and still lead to a wrong decision if the reader's situation differs. For example, a sea captain reads the data to make a decision, and a row in ground says that the freezing temperature of this ocean differs:

{"fingerprint":{"tcxp://tcxp.org/fingerprint/when":"2026-10-11T13:06:04.217Z"},"ref":"tcxp://example.com/conditions/arctic-freezing-point"}

7. Sensors

7.1 tcxp://tcxp.org/rule/11

A sensor object is a JSON object with exactly one key, sensor: an array whose entries each have exactly three keys, trigger, emit and else. trigger is a tcxp address; emit and else are each a tcxp address, or null when there is nothing to do.

When the trigger is true, emit is evaluated; when it is false, else is evaluated. All three keys are always present, so a reader never has to guess whether a missing else means "nothing" or "not sent."

7.2 tcxp://tcxp.org/rule/12

Logic primitives live at tcxp://tcxp.org/logic/<type>/<name>, where <type> is one of string, number, boolean, array or object. A trigger calls one with an @, with its inputs in params.

For example, a trigger that checks for the word yesterday, in plain form:

tcxp://tcxp.org/@logic/string/contains?{"params":[{"key":"word","value":"yesterday"}],"state":{"context":{"decide":[],"intent":[],"observe":[],"reason":[],"trace":[]}}}

8. Governors

8.1 tcxp://tcxp.org/rule/17

A governor is an evaluator: it evaluates tcxp addresses.

A governor can reference anything in the context, but it does not hold the context.

8.2 tcxp://tcxp.org/rule/25

A governor's verdict is exactly one of ACT, ASK or HALT. HALT is absorbing: once it is reached, nothing else in the same evaluation changes it to ASK or ACT.

ACT means the context is enough to proceed. ASK means something needed is missing or unresolved, so the governor asks for it before proceeding. HALT means proceeding is not allowed. The verdict decides only what happens next. It is separate from the outcome of the work itself, such as approve or reject. For example, before a request is sent to a model, a governor returns ASK while the user has not chosen which version of a file to use, and ACT once they have.

9. Documents

9.1 tcxp://tcxp.org/rule/16

A tcxp document is a text file encoded in UTF-8 ([RFC3629]), with the file extension .tcxp and the proposed media type text/tcxp. Reading, parsing or displaying it never executes it and never fetches any address it contains.

A tcxp document holds content that follows these rules; how it is used is up to whatever is using it. tcxp gives names no rules of their own: a domain follows the same rules it has in https://, and every other segment is percent-encoded from its UTF-8 bytes when sent over a network, as RFC 3986, section 2.5 requires of new URI schemes. For example, written in a document and then sent over a network:

tcxp://example.com/notes/Café
tcxp://example.com/notes/Caf%C3%A9

Reading a document returns its text and nothing else. For example, if forecast.tcxp contains tcxp://example.com/@fn/check-forecast:

const text = await fs.promises.readFile("forecast.tcxp", "utf8")
// text is the document as written. Nothing was called or fetched.
// What happens next is up to whatever is using the document.

10. Other rules

10.1 tcxp://tcxp.org/rule/4

One slash after tcxp: means a virtual address: a name in memory. It has no host and is never fetched.

A virtual address is written in plain form. It names a member of tcxp. For example, tcxp:/notes/idea-1 names, in memory:

tcxp.notes["idea-1"]

10.2 tcxp://tcxp.org/rule/6

A tcxp address is a URI ([RFC3986]), and the JSON in it is JSON ([RFC8259]). tcxp defers to both standards: no tcxp rule may allow what they forbid, and the plain form is shaped to conform to the URI.

This rule governs every other rule. When a rule and either standard could differ, the standard decides and the rule is rewritten to conform.

The plain form is the URI with its percent-encoding decoded so it can be read. The two convert into each other exactly: encoding the plain form gives the URI, and decoding the URI gives the plain form, including the JSON after the ?. Encoding follows RFC 3986, section 2.5: a name is encoded as UTF-8, and every octet outside the unreserved set is percent-encoded with uppercase hex digits (section 6.2.2), so each plain form has exactly one URI. The /, @ and ? are syntax and are never encoded. For example, plain and then as a URI:

tcxp://example.com/notes/My Notes
tcxp://example.com/notes/My%20Notes
